# Lab Reflexion-E1 — Reflection Memory Buffer

## Aim
Build just the memory mechanics of Reflexion in isolation: run a fixed task 3 times "from scratch" each time (no actual retry logic yet), but manually seed attempt 2 and 3's prompt with a hand-written reflection from the previous attempt, and observe whether performance changes. This separates "does the memory-injection mechanism work" from "can the model generate good reflections itself" (Lab Reflexion-M1 adds the latter).

## Agent Loop Shape
None yet — 3 independent single calls, with manually injected memory between them. Deliberately simplified before building the automated loop.

## Pseudocode
```
task = "Write a regex that matches valid US phone numbers in the format (XXX) XXX-XXXX only."

# Attempt 1: no memory
attempt_1 = model.invoke(f"Task: {task}").content
# ... test attempt_1's regex against a few examples, note where it fails

# Manually write a reflection based on what you observed failing:
reflection_1 = "The previous attempt's regex didn't anchor to the exact format and matched partial strings. Use ^ and $ anchors and escape parentheses literally."

# Attempt 2: with manually-written memory
attempt_2 = model.invoke(f"""Task: {task}
Reflection from a previous attempt: {reflection_1}
Use this reflection to avoid repeating the same mistake.""").content
# ... test again, write reflection_2 if still failing

attempt_3 = model.invoke(f"""Task: {task}
Reflections from previous attempts:
1. {reflection_1}
2. {reflection_2}""").content
```

## Hints & Suggestions
- Deliberately pick a task where the first attempt is likely to have a specific, identifiable flaw (regex anchoring, an off-by-one error, a missing edge case) — vague tasks make it hard to write a useful reflection by hand.
- The point of writing reflections *by hand* first is to build intuition for what a "good" reflection looks like (specific, actionable, about the mistake — not vague like "try harder") before Lab Reflexion-M1 asks the model to generate them itself.
- Test all 3 attempts against the same fixed set of test cases (valid and invalid phone number strings) so improvement across attempts is measurable, not just a vibe.

- None needed.
