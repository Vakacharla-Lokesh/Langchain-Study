# Lab H1 — Resilient Noisy-Search Agent

## Aim
Build a ReAct agent with a search tool that returns irrelevant results ~30% of the time. The agent must recognize bad results in its Thought and retry with a reformulated query — capped at 6 iterations, with a graceful "could not find a definitive answer" fallback if it hits the cap.

## Agent Loop Shape
`create_react_agent` (LangGraph) with a custom `iteration_count` field in State so the conditional edge can enforce the cap independent of the default recursion limit.

## Pseudocode
```
import random

@tool
def noisy_search(query: str) -> str:
    """Search for information. May occasionally return irrelevant results."""
    if random.random() < 0.3:
        return "Irrelevant result: Local weather forecast shows partly cloudy skies."
    return real_or_fake_lookup(query)

class AgentState(TypedDict):
    messages: Annotated[list, add_messages]
    iteration_count: int

def call_model(state):
    response = model_with_tools.invoke(state["messages"])
    return {"messages": [response], "iteration_count": state.get("iteration_count", 0) + 1}

def should_continue(state):
    last = state["messages"][-1]
    if state["iteration_count"] >= 6:
        return "force_end"
    if not last.tool_calls:
        return "end"
    return "tools"

# graph: START -> agent -> conditional(should_continue) -> {tools -> agent, end -> END, force_end -> fallback_node -> END}

def fallback_node(state):
    return {"messages": [AIMessage("I could not find a definitive answer after several attempts.")]}
```

## Hints & Suggestions
- Prompt the model explicitly to critique its own search results ("If a result seems irrelevant to the question, say so and try a different query") — this is what turns "Thought" from decoration into actual recovery behavior, echoing Lesson 04's theory.
- Run this 10 times and track: (a) how often it recovers from a noisy result within the cap, (b) how often it hits the cap and falls back gracefully, (c) whether it ever answers confidently based on a bad result (the failure mode you're specifically trying to avoid).
- The `iteration_count` field needs a reducer decision too — since it's a plain int (not a list), returning the new value each time *overwrites* it correctly by default (no `add_messages`-style reducer needed) — but confirm this is actually what's happening by printing it each step.

## Free APIs / Data to Use
- For a more realistic version, swap `noisy_search` to genuinely call a free API and occasionally query it in a way likely to return unhelpful results (e.g., a deliberately vague query against Wikipedia's search API) instead of a hardcoded random failure — more true-to-life noise than a coin flip.
