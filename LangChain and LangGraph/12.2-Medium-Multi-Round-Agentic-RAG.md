# Lab AgenticRAG-M1 — Multi-Round Agentic RAG

## Aim
Build a larger document set (15-20 chunks covering a few related sub-topics) and ask a question that plausibly needs **two separate retrieval calls with different queries** to fully answer — proving the agent can reformulate and retrieve again, not just retrieve once and stop.

## Agent Loop Shape
`create_react_agent` (or hand-built LangGraph ReAct loop) with the retriever tool — same as Lab AgenticRAG-E1, but testing genuine multi-round behavior.

## Pseudocode
```
docs = [
    # Sub-topic A: several chunks about "Project Falcon" architecture
    # Sub-topic B: several chunks about "Project Falcon" deployment process
    # A few unrelated distractor chunks about other projects
]
vectorstore = InMemoryVectorStore.from_documents(docs, embedding=embeddings_model)
retriever_tool = create_retriever_tool(vectorstore.as_retriever(k=3), name="search_docs",
    description="Search internal engineering documentation.")

agent = create_react_agent(model, tools=[retriever_tool])

question = "What database does Project Falcon use, and what's the deployment process for updating it?"
# Ideally requires: retrieve architecture info (database choice) -> retrieve deployment info separately
result = agent.invoke({"messages": [HumanMessage(question)]}, config={"configurable": {"thread_id": "m1"}})

for m in result["messages"]:
    print(m)
```

## Hints & Suggestions
- Split the question's two halves across genuinely different chunks (don't let one chunk answer both parts) — this forces the agent to actually reformulate its query for the second half rather than reusing the first retrieval's results.
- Count how many times the retriever tool was actually called by walking the message trace — if it's only called once despite the question needing two distinct lookups, that's a sign the first retrieval's `k` is too generous (accidentally pulling in both sub-topics at once) or the question needs to be more clearly two-part.
- Try lowering `k` to 1-2 to force the agent to work harder across multiple rounds, and observe how that changes its retrieval strategy.

## Free APIs / Data to Use
- None required — construct your own document set, or use real content from a project you know well (e.g., your own README/docs from one of your GitHub repos) for a more realistic test.
